WHAT THIS IS
You are reviewing a change to ItemGuard Premium (branch `premium-mysql`, Paper 1.21.11, Java 21,
MySQL 8.4 behind a shared schema). The change fixes a defect that two runtime gates had been hiding
behind a race, and it lands on top of three other defects fixed the same day. Judge the design, not the
prose.

THE DEFECT THAT WAS FIXED (found by re-running gates, after months of green offline suites)
`ItemSqliteRepository.completeObservationEpoch(...)` pruned observations by epoch:
    DELETE FROM item_observations WHERE scan_epoch < ?
called at the end of every completed audit, with no `server_id` clause, on a table that M3 had just
given `server_id` plus the index `(item_uuid, server_id, observed_at)` for exactly one question:
"which servers has this identity been seen on inside a window" (`cross-server-window-minutes: 30`).
Consequences, both reproduced:
  - the two-Paper fixture can never observe `SEEN_ON_MULTIPLE_SERVERS`: server-2's completed audit
    deletes the rows server-1 wrote seconds earlier;
  - a migrated target loses `item_observations` on the first audit after startup while every durable
    table survives.
Both gates had been passing by winning a race against that audit (30 s scan interval). Under load the
audit won and both gates went red twice in a row.

THE CHANGE
1. The prune is time-based: `DELETE FROM item_observations WHERE observed_at < ?` — one statement,
   used by both completion paths (`completeObservationEpoch` and `completeObservationEpochAndAudit`).
2. New config key `anti-dupe.observation-retention-minutes` (default 30), floored at two scan cycles by
   `AntiDupeSettings.observationRetention(...)`, mirroring the floor already used for the detection
   cooldown. `DatabaseManager` computes the cutoff (`now - retention`) and passes it down.
3. The old public signatures (`completeObservationEpoch(long)`, `completeObservationEpochAndAudit(...)`)
   remain and delegate with a constant default window (`DEFAULT_OBSERVATION_RETENTION_MILLIS = 30 min`),
   so tests and any caller without config keep compiling.
4. `ObservationRetentionTest` pins both halves: a fresh row from another epoch survives an audit, an
   expired row does not.
5. The migration gate's restart expectation was rewritten: durable tables must match exactly,
   `item_observations` is asserted only to be inside {0,1} with the retention rule recorded in the
   receipt, instead of asserting that nothing ever expires.
6. Several pre-existing tests used epoch-shaped timestamps as observation times (`39L`, `1000L`), which
   a retention window treats as expired. Their fixtures now stamp such values with the current time
   (`nowIfFixtureEpoch`), with the reason written at the helper.
7. Contract doc + owner runbook: the retention rule, why it changed, and the instruction to keep
   retention ≥ the cross-server window.

EARLIER DEFECTS FIXED THE SAME DAY (same session, all with tests)
  a. `arm()` returned the pre-transition claim record (state PENDING) while `settle()` refuses anything
     that is not PREPARED: every issuance armed the claim, delivered the item, wrote nothing, left the
     identity locked in PREPARED for ever and told the player it had succeeded. Fixed by carrying the
     moved claim (`ReclaimClaim.movedTo`).
  b. The success message followed the delivery flag rather than the recorded outcome, hiding exactly the

  c. `/finditem giveoldid` ran its absence check on the async dispatch, so the inventory presence probe

     given, with a message that read like an ordinary "absence not proven" verdict. Fixed with a hop
     back to the server thread and a contract test against the two swapping back.
